# SmartSolar redesign — implementation report

Date: 2026-10-06. Release target: mobile 1.0.0 (12), existing bundle identifier `com.dshapar.solar`.

This report records implementation and verification against [DESIGN_SPEC.md](DESIGN_SPEC.md), [CLAUDE_CODE_PROMPT.md](CLAUDE_CODE_PROMPT.md) and the approved [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md). ## Mobile foundations and navigation

The installed stack is Expo 57.0.23, React Native 0.86.3, React 19.2.3, React Navigation 7, native-stack 7.16.0 and react-native-screens 4.26.0. `react-native-bottom-tabs` and `@bottom-tabs/react-navigation` 1.4.0 were adopted on iOS after an actual Release compile and simulator navigation/theme/lifecycle checks. This is a custom native build, not Expo Go. iOS uses native tabs, SF Symbols, platform material and haptics. Other platforms retain React Navigation's custom floating capsule with SDK-matched `expo-blur`; no Android native run is claimed.

The four tabs are Home, Energy, Devices and Automations. Home contains Live readings, Readings log and Settings; Settings contains all installation, preference and account destinations. Energy contains Production and Export segments. Automations contains the list and Activity. Device details and hourly tables use native sheets; Connect and Paywall are modal flows. Auth has Welcome, code request/entry, password fallback and server selection. Account settings remain reachable when a subscription expires.

Source: `mobile/src/application/AppNavigator.tsx`, `navigationTypes.ts`, `AuthContext.tsx`, `AppProviders.tsx`.

Navigation memory is scoped to the current API, account, durable session and demo boundary, above the subscription gate. A foreground access check keeps the authorized navigator mounted while the current grant is still valid. A denied or expired grant closes access; an authoritative server deadline is applied before slower native work. Account/session replacement clears remembered state. Existing StoreKit receipt ownership, server verification before finish, durable retry and wall/monotonic deadline behavior are preserved.

Tokens come from `docs/redesign/tokens.json` through `scripts/generate-design-tokens.mjs`; the generated native output is `mobile/src/ui/theme/tokens.ts`. Theme and font startup live in `ui/theme/ThemeProvider.tsx`, `FontBootstrap.tsx` and `fonts.ts`. Light is the initial preference; Dark and System are explicit options. The native Appearance bridge follows that choice so UIKit sheets/tab material match the app. A late storage read cannot overwrite a newly chosen appearance.

Onest 400/500/600/700 and Unbounded 700 are self-hosted static TTFs under `mobile/assets/fonts`, with both OFL notices. `expo-font` embeds the native fonts and checks runtime readiness; no external font download is needed. CJK uses platform fallback. Shared components, fields, selectors, status pills, chart/table patterns, skeletons and error/empty states are in `core/components.tsx` and `ui/`. `ui/forms/CompassBearing.tsx` supplies a token-themed dial with accessible cardinal presets bound to the numeric field. `ui/DesignGalleryScreen.tsx` is reachable only in development through the Home avatar's long press.

Visible branding, icon and permission strings use SmartSolar. Internal project/package names, bundle ID, `deyesolar` callback scheme, API contracts and StoreKit product IDs are retained for compatibility. `mobile/plugins/withSmartSolarNative.cjs` preserves native assets and removes background-location/motion declarations; location is requested only from the explicit foreground location action. Localized Face ID/location strings are generated for all 15 locales.

## Compatibility and deliberate adaptations

- New mobile/API contracts are additive. Existing build 11 auth, session, Google PKCE, account-security export, device command, history/forecast and billing behavior remain supported. New response contracts validate nullable facts and optional additions; a missing new capability never enables a control. Authentication proofs do not expose bearer tokens to screen code, and stale session/account action results are fenced.
- Native iOS tab material, SF Symbols and platform metrics intentionally follow UIKit rather than reproducing the custom HTML capsule pixel for pixel. The custom non-iOS capsule remains in source; Android execution is outside the verified scope.
- Provider model, location, renewal, “changed ago”, added date and support facts are shown only when supplied. A trusted pinned provider display name may be shown; raw provider IDs remain support information. No guessed model or provider capabilities are created.
- Sunset does not prove battery supply. The battery sentence requires fresh valid signed flow; night forecast/current-hour gaps do not become measured zero. Completed export hours and a current hour in progress have separate wording and totals.
- Hourly/daily energy uses measured coverage, not power multiplied across unknown intervals. Command requests and provider receipts are not backfilled as physical device history. Coverage/price gaps remain visible. CSV UI is the web surface specified in B5/B6/B10; the mobile hourly/table views do not pretend to export a CSV.
- Local StoreKit fixtures and native UI API fixtures are explicitly synthetic. Native UI checks exercise the real subscription gate and navigator with a fictional account; they do not demonstrate a production payment or Apple identity provider configuration.
- Formatted localization preserves literal device/rule/provider names. If two distinct translated templates produce an identical rendered label, the bounded provenance cache records that ambiguity and retains the already localized wording instead of guessing a different action on a language switch. An explicit template plus arguments always resolves the intended action. A simultaneous Disable/Disconnect collision regression covers this case.

## Apple operator prerequisite

Implementation of Sign in with Apple does not make the current server configured. At this checkpoint the production `Auth:Apple` configuration is absent; the required operator key/account details are pending. Apple availability must therefore remain false and the UI must hide its action until configured and verified.

The operator must enable Sign in with Apple for native App ID `com.dshapar.solar`, include it in the distribution provisioning profile, associate a web Services ID and register `https://solar.dshapar.com/auth/apple/callback`. Required server settings are `Auth__Apple__Enabled`, `NativeClientId`, `ServicesId`, `TeamId`, `KeyId`, `PrivateKeyFile` (or protected secret-injected `PrivateKeyPem`) and `CallbackUrl`. The P-256 `.p8` signing key remains a protected server secret. Preserve the durable Apple revocation outbox and auth data-protection keyring in matched backups. These credentials are separate from App Store subscription verification. Exact configuration and live verification steps are in [accounts-deployment.md](../accounts-deployment.md).

### Backend and deployment verification

The additive backend supplies unified verified-code auth, Apple identity/nonce/revocation handling, scoped account/session/preferences, integration status, stable activity/readings pagination, device history/controller metadata, atomic display-name selection and versioned installation settings. Every interactive read/action retains current installation and permission checks. Display labels preserve provider identity, command capability data, bindings and existing local labels. The new capabilities migration adds the required tables/columns/indexes without replacing existing account, billing or installation records. Its downgrade is rejected before touching schema or data. Existing production integration packages remain pinned and byte-identical. The separate migration-only job uses the existing privileged connection; the running application retains its restricted SQL principal. Historical PV validity repair is the explicit, tested exception to unchanged old-row hashes; measurement values and provenance are preserved.

Final verification includes all five .NET test projects against actual SQL Server, live Blazor/browser billing revocation and deadline cases, nullable measurements and current-hour export semantics, scoped integration selection/rename and permission/disposal/version races. The full solution gate passed **1,503 tests, zero failures and zero skips** across Web 1,031, Infrastructure 269, Integrations 93, provider E2E 88 and Rule Engine 22. Browser inspection then identified three native HTML attribute corrections and two string-parameter bindings; the final solution rebuild and **83 targeted cases** passed, including 16 new field-markup cases and the actual SQL-backed Readings page. Across these two runs, 1,520 distinct cases passed; the 83-case subset overlaps the full run and is not an additional unique total. Exact TRX counters, the narrow source delta and final source fingerprints are retained in private `source-gates-final.json`. Dependency audit found no direct or transitive NuGet advisories. Local provider/browser/native fixtures do not issue real hardware commands, payments, email or SMS.

The production procedure is documented in [production-redeploy.md](../production-redeploy.md). It first validates the exact candidate on an isolated restore of the coordinated encrypted backup, including byte-preserved keyrings/configuration, additive/repeated migrations and the actual released build-11 response validator. A durable migration-launched marker prevents automatic old-binary restart after failure. Runtime privileges, original records/pins/secret files, both disabled rules and neighboring container identity/start/restart state are checked. Fresh Google login, actual provider observations and public readiness are verified after cutover; their results are operational receipts outside this source checkpoint.
