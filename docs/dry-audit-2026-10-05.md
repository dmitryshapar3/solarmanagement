# DRY-аудит, 5 октября 2026

Аудит охватывает собственный код сервера, домена, интеграций, мобильного приложения, Razor, тестовых fixtures и build/operations scripts. Зависимости, generated build output и сгенерированные EF designer/model snapshots не используются как цели для удаления повторов. Рукописные миграции включены; их история сохраняет воспроизводимость обновления базы.

Механический inventory и поиск одинаковых блоков воспроизводятся командой `python3 scripts/audit-dry.py --report /tmp/solar-dry.json`. Они дополняют проверку ответственности, контрактов, отмены, транзакций и безопасности; отсутствие текстовых клонов само по себе не доказывает DRY или SOLID.

## Общая логика и её владелец

| Повторявшаяся ответственность | Изменение и граница |
| --- | --- |
| HTTP response bounds, публичная сеть и DNS pinning | Отдельный BCL-проект `SolarManagement.Http`: `BoundedHttpContent`, `PublicHttpTransport`, `PublicNetworkAddressPolicy`. Web и WorkerSdk используют один механизм; статус и ошибки классифицирует адаптер поставщика |
| Повторы idempotent HTTP reads, deadlines, `Retry-After` | `RetryingJsonReader`, `IJsonDocumentReader`, provider policies и внедрённый `TimeProvider`. Open-Meteo и PSE сохраняют собственные URI/depth/units/pagination правила; мутации устройств не повторяются этим transport |
| Декодирование Open-Meteo series | `OpenMeteoSeries`: units, arrays, numeric ranges, roof intersection, variability. Текущий прогноз, завершённая история и satellite native timeline проверяются соответствующим source |
| Примитивы vendor JSON | `CloudJson`: scalar decoding и epoch bounds. Inverter numeric text, socket string и различная допустимость дробных timestamps остаются явными параметрами |
| Проверка signed package manifests | Один `ReadVerifiedManifest` для install и installed verification. Подпись проверяется по исходным байтам; catalog equality и payload coverage имеют собственные проверки |
| Хранение настроек и defaults | Cached `SettingsSchema` и `InvariantSettingCodec` для reads/writes/runtime defaults/fingerprint. Операторский API key исключён из persisted/editable settings |
| Ограничения физических параметров | Общая domain policy геометрии площадки; API сохраняет собственные строки ошибок и продуктовые ограничения |
| Правила: defaults, validation, configuration ownership | `RuleConfigurationPolicy`, `RuleConfigurationSnapshot`, execution projection. Name участвует в client concurrency version, а runtime state не перезаписывается редактированием конфигурации |
| Правила: решение и объяснение | `IRuleDecisionEvaluator` возвращает immutable `RuleDecision`; executor и history используют принятое решение. Перед физической командой повторно проверяются актуальность, права и конфигурация |
| Auth, CSRF, roles и session predicates | `AccountSessionValidator`, `AuthenticatedMutationPolicy`, `InstallationPermissionPolicy`. Успешная CSRF проверка кешируется только внутри request; cookie+bearer требует CSRF. SQL fences и account/installation границы сохранены |
| Capabilities и eligibility интеграций | Typed capability reader и transaction-bound eligibility helper для rules/socket/source операций |
| Ошибки API | `ApiProblem` и scoped `ApiProblems` renderer/map. Сохраняются machine code, human message, status, no-store, traceId и Retry-After |
| Формы мобильного приложения | `ScopedActionScope`/`useScopedAction`: busy, identity/session generation, disposal и late completion. Бизнес-проверки подтверждения личности остаются в соответствующем controller |
| Команды устройств на мобильных экранах | `SocketCommandActions`, общий notice/status presenter. Idempotency и recovery по-прежнему принадлежат command coordinator; blur не откатывает физическую команду |
| Группы read refresh | `RefreshGroup` ждёт завершения всех sibling requests; ранняя ошибка не открывает параллельный повтор группы |
| Razor query/timer lifecycle | `AsyncQueryScope`: cancellation, selection ownership, disposal и refresh loop. SQL queries, фильтры, formatting и selections остаются компонентам |
| Диапазон и срок истории | `HistoryQueryPolicy` задаёт фильтрацию, ordering, лимит строк и единый предел 168 часов для API/Razor и retention журналов правил. Один injected-clock snapshot задаёт timestamps и cutoff записи |
| SQL fixtures и UI preview artifacts | Общий lifecycle изолированной SQL базы, options/HTTP fixtures и render preview exporter. Специфические auth hosts, seeds, interceptors и сценарии сохраняются в тестах |
| Историческая telemetry quality | Reading сохраняет явные validity flags. SOC и power в rule history допускают отсутствие; API и интерфейсы не превращают его в 0. Новая forward migration сохраняет старые значения без догадок о качестве, новые flags для них — false |

Vendor options/models Deye и Shelly принадлежат соответствующим provider projects; общий wire contract не содержит vendor-specific configuration classes. Новый HTTP-проект не зависит от домена или worker runtime. Изменённый payload получает новые immutable версии: Deye/Shelly `1.0.4`, остальные восемь providers `1.0.3`.

Demo после перехода на GUID получает мощность из явной device policy, а изменение цели правила — наблюдаемое состояние нового устройства. Native Info.plist получает version/build из Xcode settings; отдельные зафиксированные значения удалены.

## Повторы, которые требуют самостоятельных проверок

Authorization и SQL predicates проверяются повторно на границах admission/transaction/physical command. Это защита от изменения прав и конфигурации между этапами. Свежесть SOC, customer package pin, tenant identity и uncertainty recovery сохраняют свои отдельные fences.

Razor/C#/TypeScript имеют разные языки и runtime. Общая rule policy C# и TypeScript сверяется по одному набору из 21 golden vector; сетевой server остаётся авторитетным валидатором. Migration designer/model snapshots генерируются EF и не объединяются с историческими версиями.

## Механическая проверка повторов

Inventory включает 565 собственных source files и 63 644 строки. Scanner нашёл четыре группы одинаковых блоков: три группы тонких test-host catch/dispose call sites, использующих общий `TestHttpHostCleanup`, и одну историческую schema definition в EF migration Up/Down. Lifecycle базы и приложения уже имеет общего владельца. Исторические schema definitions не переписаны: одинаковые определения в старом Up и последующем Down нужны для воспроизводимости миграций. Каждая группа проверена по назначению.

Результат следует оценивать вместе с ответственностями в таблице: повторная проверка разрешений на разных границах и отдельные vendor/time-series predicates обязательны для поведения системы.
